# Deploy to your Cloudflare account

The repository now has a Wrangler configuration for a direct Worker deployment. It is intentionally not deployable as a complete game until the account-specific D1 binding and runtime settings are configured. The existing Sites manifest remains for rollback; this workflow does not deploy to Sites.

1. Create a D1 database named `hourmuz` in the selected Cloudflare account. Add the real database ID to `wrangler.jsonc` under `d1_databases` with binding `DB`, database_name `hourmuz`, and migrations_dir `drizzle`. Do not use a fabricated ID.
2. Authenticate Wrangler against that account, apply the migrations using `wrangler d1 migrations apply DB --remote`, and deploy using `wrangler deploy`. The build writes the site to `dist/public` (pages, hashed JS and CSS under `/assets`, security headers in `_headers`) and the API-only Worker to `dist/server/index.js`. `wrangler deploy` uploads both: Workers Static Assets serves the site and only `/api/*` and `/owner-login` run the Worker, so asset requests are not billed Worker invocations. A host without a static-assets layer can embed the site into the Worker with `INLINE_ASSETS=1 npm run build`.
3. `APP_ORIGIN` is set in `wrangler.jsonc` (`https://ishormuzopen.fun`; change it if you deploy elsewhere). Put `AUCTION_OWNER_EMAIL`, `CF_ACCESS_AUD`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and, optionally, `RATE_LIMIT_SECRET` (any long random string that keys the per-minute client hash) into encrypted Worker secrets with `wrangler secret put`, so the owner address never appears in the public repository. The keys previously saved in Sites do not automatically transfer. Optional plain variables: `TIP_URL` (a Stripe Payment Link for the results-screen tip button), `SPONSOR_DAY_PRICE` and `SPONSOR_WEEK_PRICE` (whole cents); see `docs/sponsorships.md`.
4. Configure a Cloudflare Access application with an allow policy for the owner's email. During Stripe testing, protect `/sponsor`, `/sponsor-admin` and `/api/sponsorship*` using this same audience. Leave the game, stats and Stripe webhook public. Owner identity comes from runtime `ctx.access`, with audience and email checked in server code. Spoofed identity headers cannot authorize an owner. There is no other sign-in path: the legacy Sites header identity was removed, so owner pages only work on hostnames that Access protects.
5. Test with Stripe test keys. Test bookings are stored separately and never appear in the game or the public sponsor list. Register the new origin's `/api/stripe/webhook` endpoint in Stripe with the events listed in `docs/sponsorships.md`; the old `chatgpt.site` webhook does not follow a domain move. Confirm a day booking, a week booking, a rejected double booking and a stale-hold refund.
6. Before live launch, narrow Access protection to `/sponsor-admin` and `/api/sponsorship/admin` so sponsor checkout is public. Keep the audience configured. Switch to live Stripe keys and the live endpoint signing secret only after real test-mode verification. No live payment is authorized by merely running tests.
7. After the domain is owned and active in Cloudflare, bind it as a Worker Custom Domain. Update APP_ORIGIN and Stripe webhook URLs to that verified domain. The canonical and social-card URLs already point at `https://ishormuzopen.fun`; set `SITE_ORIGIN` at build time only to repoint them for another deployment. Consider disabling workers.dev once the domain and Access policy work.

Plan sizing: verifying a ranked score replays the whole round on the server and takes roughly 10 to 20 ms of CPU, so check that against the per-request CPU limit of the chosen Workers plan (the free plan allows less). Rate limiting and presence check-ins write a few D1 rows per minute for every open game tab; cached reads cost nothing, but budget D1 writes for the expected number of concurrent players.

Current data remains on the original managed D1 database. A fresh Cloudflare D1 database does not transfer leaderboards, analytics or sponsor records. Export/import requires a separate data migration before cutting over if that history is needed.

Owner Access must be verified on the deployed Worker before payments are enabled. Missing runtime Access identity fails closed. No Cloudflare account, database, route, DNS or billing changes have been made by preparing these files.
